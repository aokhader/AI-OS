# HandsOff — Design Report

HandsOff gives an AI agent hands inside legacy bank software that has no API. A model drives the UI once to accomplish a stated goal; the run is compiled into a typed, versioned **capability**; from then on the capability replays deterministically with no model deciding anything, under an explicit result contract, a policy gate on every action, and an escalation path that hands the live browser session to a person and takes it back. The target is a locally built mock of a vendor core-banking product (framesets, table layouts, no ids or labels) deployed by two fictional institutions, with injectable runtime conditions. Everything here is built and tested unless it says "designed"; `/evidence/`, indexed in the README, holds two real model-driven discovery runs (Gemini 3.5 Flash Lite) and eight replays.

## 1. Architecture

One process. The `handsoff` CLI owns the Playwright browser, runs discovery or replay, and, when a run may need a person, serves the console API itself for the run's duration. No queues, workers or services; the session broker the real environment wants is documented, not built.

Six packages, one dependency rule. `core` holds the zod schemas, both engines, the compiler, the condition classifier, the policy gate, the redactor, the planner protocol and the filesystem store, and imports nothing but zod and Node. `surface-playwright` implements the `Surface` port; `llm-anthropic` and `llm-openai` implement the `Planner` port (the second speaks the OpenAI protocol, which is how the discovery runs came from Google's free tier). The console imports only types from core; the mock app imports nothing from the workspace. The rule makes "no model on the replay path" a checkable fact.

The decisions that shaped it, with their cost:

- **Perceive through an accessibility-style tree plus a screenshot; act through Playwright.** A walker in every frame emits role, accessible name, value, states, bounding box, frame path and structural path per node, derived from HTML semantics because legacy markup has no ARIA. The model sees the tree as compact text plus the screenshot; replay resolves targets over the same tree. It works where selectors and ids do not exist, and the node shape is what a desktop accessibility API yields too. Cost: a walker of our own, and native dialogs, which block script evaluation, had to be raced.
- **The planner protocol lives in core; adapters translate wire formats.** Swapping providers was configuration, which mattered when the first free tier ran out.
- **Compile is rule based.** Every artifact field traces to a recorded event: waits pruned, parameters bound by provenance, locators derived from the element acted on, checkpoints proposed from observation deltas.
- **Errors are data across every seam.** Verdicts, resolutions, classifications and results are discriminated unions; exceptions are for programmer errors.
- **A mock target over a public site**, so that session expiry, interstitials, busy and error pages, validation rejections, relabelled controls and a second tenant could be injected on demand.

## 2. Artifact schema

A capability is a contract first and a step list second: identity, integer `version`, `status` (`draft`, `approved`, `retired`), provenance; a binding to an app profile by product, never to a tenant; an `entry`; typed `inputs` and `outputs`, each with a `sensitivity` (outputs also carry a parser and a source); ordered `steps`, each with the model's intent, an action, a target, preconditions, a `postcondition` that is its checkpoint, `risk`, `confirm`, bindings, the discovery `baseline` and who recorded it; a `success` condition; `detectors` for the business outcomes the flow can end in; a `policy` block listing risky steps; and `variants` for per-tenant overrides. A JSON Schema is exported per artifact type.

Four shaping choices. **Parameters bind by provenance, not by value**: a typed value is `{ param: "memberId" }` because the model called the parameter tool, so a sensitive value never enters the transcript and a coincidental match can never bind (whole-segment URL canonicalisation is the one exception, marked `inferred`). **Targets are ranked strategies, not one selector**: `role` (role plus accessible name), `anchored` (relative to stable text: the textbox labelled "Member #", the Balance column of the row whose first cell is "Savings"), then `structural` (frame path plus positional path) as the last rung; anchors never contain parameter values or data-looking text, and a table row keyed by the parameter contributes no anchor, the rule that stopped a discovered artifact from anchoring on a member's name. **One `Condition` type in three roles**: preconditions gate a step, postconditions are its checkpoint, detectors carry a class (`outcome`, `recover`, `fail`, `escalate`) that says what replay does when they match. **The discovery resolution is a recorded baseline** (which strategy resolved, how many candidates), so replay measures drift instead of guessing it.

## 3. Determinism & error handling

Replay signs in through the profile's routine with credentials from the environment, opens the entry route, and runs every step the same way: wait for preconditions, resolve the target by walking the strategies and requiring exactly one visible match, pass the policy gate, act, wait for the postcondition. Detectors are evaluated on every poll of every wait, so a sign-in or error page is seen at once rather than after a timeout, and a native dialog cannot stall a wait.

One ordered classifier decides what a matched condition means, with a precedence that settles the ambiguous cases: session-level conditions first (a sign-in page that also says "error" is an expiry), then fatal pages, known interstitials, business outcomes limited to their steps, escalate-class conditions, and last the step's own checkpoint. `dismiss` and `wait-retry` recoveries run inside the wait; a session expiry signs in again and re-runs the flow from its entry, counting attempts per step and refusing after a risky step has executed. Budgets, from policy, are two recoveries per step and one re-bootstrap per run.

The result has three terminal statuses. `success` carries the outputs; `outcome` carries a code such as `MEMBER_NOT_FOUND`, because "no such member" is an answer, not a crash; `failure` carries a kind (`TARGET_NOT_FOUND`, `CHECKPOINT_FAILED`, `UNEXPECTED_STATE`, `APP_ERROR`, `TIMEOUT`, `POLICY_BLOCKED`, `DRIFT_SUSPECTED`, `ESCALATION_ABANDONED`), the step, what was expected and what was observed. Every result also reports the steps run with attempts and how each target resolved, the recoveries, an `escalation` block when a person was involved, and `sideEffects` as `none`, `possible` or `committed`, derived from whether a risky step executed and whether its checkpoint was confirmed: a timeout after a submit is not a timeout before it.

Drift is secondary and measured: a step resolving by a deeper strategy than its baseline is reported as `drift`; a tenant fingerprint that does not match is `DRIFT_SUSPECTED` before any step runs. For a target no strategy finds, the one bounded model call on the replay path is the assisted fallback: behind a policy switch, one proposal from the discovery planner, which must target an element of the page it was shown, passes the gate, is refused if risky, and is re-verified against the step's own checkpoint; if it fails, the original failure stands.

## 4. Heterogeneity & multi-tenant

The seam between "how we perceive and act" and "the recorded flow" is the `Surface` port: `observe()` returns nodes with role, name, value, bounding box, frame path and structural path plus a screenshot; `act()` takes the small action vocabulary against a ref from the last observation; `captureHumanActions()` reports what a person does. Target resolution is a pure function in core over the nodes. A desktop app would implement the same port over an accessibility API such as Windows UI Automation: control type, name and grid semantics feed the `role` and `anchored` strategies unchanged, automation ids replace the structural rung, `navigate` becomes a menu path recorded in the app profile, and screen ids replace URLs in conditions. The artifact schema does not change.

Tenants reuse through the **app profile**, one per vendor product: the sign-in routine, the shared detectors, and the known variants, each with a fingerprint and overrides. Once the entry page is open, replay fingerprints the session; a requested variant must match, otherwise exactly one variant must, and anything else is `DRIFT_SUSPECTED`, never a silent attempt against the base variant. The profile's overrides then rewrite the capability in memory (label maps over role names, anchors, columns and text predicates; route maps; a frame map, because the second tenant renames its main pane; extra detectors), then the capability's own per-step replacements, and the rewritten artifact is validated before it runs. The evidence shows the capability recorded on tenant A succeeding on tenant B, which relabels three controls, renames the frame and reorders the account columns, every step resolving by its first strategy. A registry of fingerprints and a per-variant replay history feeding a stability score that gates `approved` are design only.

## 5. Escalation & handoff

"Stuck" is a classification with six causes sharing the failure vocabulary: the model asked for a human, the stuck detector fired (three identical actions, or three with no observable change), the gate required confirmation for a risky step, an escalate-class condition matched, a recovery budget ran out, or a replay failed in a way a person could fix. The last two are raised only when policy allows and an operator is attached; unattended runs fail as classified. Every cause takes one path: the engine observes the page, writes the intervention request (capability or goal, run and step, cause and detail, masked screenshot, suggested hand-backs) to the store and the run folder, and moves the control owner from `automation` to `awaiting_operator`.

Who is in control is a state machine in core (`automation`, `awaiting_operator`, `human`, `aborted`), and the engines reach the surface only through a guard that refuses unless the owner is `automation`, so the console cannot race the engine. Claiming moves the owner to `human` and starts capture: a script the surface injected into every frame reports each click, value change and Enter-key submit with the element's role, name, value and structural path, and the engine turns each into a step with a locator derived from the last observation exactly as automation steps are. The person works in the very window automation was driving: same session, cookies and frames. Hand-back has four forms: `approve_step` lets automation run the step it asked about; `resume` runs a checkpoint scan, evaluating the postconditions of the current and following steps against a fresh observation and continuing after the last one that holds; `mark_complete` verifies the success condition and re-extracts every output from the live page, so the operator never types a result; `abort` ends the run with the failure that caused the escalation. Nobody claiming within the policy timeout ends the run `ESCALATION_ABANDONED`; a claimed session belongs to the person until they hand it back. In discovery the person's steps join the recording, so a run that needed help still compiles.

The operator surface is minimal but real: the console's inbox and detail with claim, hand-back and a live feed of human actions pushed over a WebSocket from the process that owns the browser, plus a terminal prompt with the same choices. The handoff evidence went through the real console API with a script standing in for the hand at the window, since this environment cannot show a headed browser; the README says how to do it by hand.

## 6. Safety

Policy is one file. The gate runs before every `act` in both engines, the sign-in routine, recovery clicks and assisted proposals included. It checks the action kind against an allowlist, the origin and route of a navigation against allowed origins, denied routes and allowed routes, and classifies **risk from the live page**: the control's accessible name against risky patterns, the action of the form it belongs to, the current or target route. At replay the effective risk is the higher of recorded and live, and a disagreement is a mismatch event. A step recorded safe that classifies risky needs a person whatever the approval state, since the approval covered an artifact that did not declare the risk; a recorded risky step runs unattended only on an approved capability with `confirm: none`, asks every time with `confirm: operator`, and is blocked on a draft. Belt and braces, the browser layer answers any navigation to an origin outside the allowlist with a block page, and a runtime detector fails the run if it lands there.

Sensitive data never reaches the model or the disk in clear. The model sees parameters by name and a redacted observation; everything persisted carries `«name#sha256:…»` in place of a sensitive value, so runs on the same value can be correlated without storing it; screenshots are masked by painting over every element whose text shows the value before capture; outputs marked sensitive are returned to the caller and masked in the persisted result; credentials exist only as environment variable names. The limits, plainly: risk classification is heuristic and a destructive control with a bland label would pass; a sha256 prefix of a five-digit member number is a correlation handle, not encryption; a value a person types during a handoff is recorded in clear unless it equals a declared parameter; there is no data-loss scan of page text; the console and API have no authentication.

## 7. Cuts

- **Remote co-browsing.** The handoff works on the same machine through the headed window. Next: a session broker owning browser contexts, a screencast or VNC bridge to a remote console, operator authentication, leases that return an abandoned claim to the inbox, an audit trail. The control-owner machine and the escalation record would not change.
- **Desktop surface.** Designed as a second implementation of the `Surface` port (section 4). Next: build it against one native app and learn where focus and dialogs bite.
- **Multi-tenant at scale.** One second tenant proves the override model; the fingerprint registry, per-variant replay health and a stability score gating `approved` are design.
- **Multi-run stability.** Replaying N times and reporting flakiness is the check I would add first; the per-step resolution report already gives it something to aggregate.
- **Agent-facing catalog and code generation.** Capabilities are files with a contract and a JSON Schema; a catalog endpoint that invokes one by name with typed arguments is a thin layer over `replay()` that was not written, nor was emitting a test file from an artifact.
- **Hardening.** Keyed hashes for low-entropy values, a data-loss scan of typed human input, authentication on the console, continuous integration.

The one stretch goal taken was the assisted fallback, because it is the sharpest test of the safety story: a model on the replay path that can only ever do one gated, verified thing.
